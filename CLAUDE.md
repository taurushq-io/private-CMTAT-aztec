# Agent guide — private CMTAT on Aztec

> **Note — keep in sync:** `AGENTS.md` and `CLAUDE.md` must always be **identical**. Any edit to one must be applied verbatim to the other.

> **Note — commit messages:** After each group of modifications or each feature added, always provide a **one-line GitHub commit message** (Conventional-Commits style, e.g. `feat: ...`, `fix: ...`, `docs: ...`).
>
> **Never put `!` in a commit message** — not as the breaking-change marker (`feat!: ...`), not anywhere else. In an interactive bash, `!` inside double quotes triggers history expansion, so `git commit -m "feat!: ..."` aborts with `bash: !: unrecognized history modifier`. Signal a breaking change with an uppercase `BREAKING CHANGE:` line in the commit body instead, and keep the subject line free of `!`.

> **Note — no tool names in the changelog:** never name an assistant tool, skill or slash command in `CHANGELOG.md`. The changelog records what changed in *this project*, for readers who have no idea what tooling produced it. A line ending "the `<some-skill>` skill gained the corresponding check" documents the author's toolbox rather than the release, and it rots independently of the repository — the tool can be renamed or deleted, leaving a dangling reference to something the reader could never have seen. Describe the change and its effect; if the tooling matters, record it in the audit or analysis report instead.
>
> This is about **tool identities, not the word "Claude"**: files committed to the repository — `CLAUDE.md`, `AGENTS.md`, `CLAUDE_AUDIT.md`, `CLAUDE_ANALYSIS*.md` — are cited freely, because a reader can open them.

> **Note — do not hard-wrap prose in `CHANGELOG.md`:** one line per bullet or paragraph, and let the editor soft-wrap. Markdown collapses a single newline into a space, so a hard-wrapped bullet renders identically — the cost is invisible in the published changelog and paid entirely in the repository. Changing one word reflows every following line, so a one-word correction arrives as a multi-line diff in which a reviewer cannot see what actually changed; and because the wrap column depends on whoever wrote the entry, the file drifts into a mix of styles that reads as damage. Keep the line structure only where it is semantic: fenced code blocks, tables and blockquotes.

> **Note — long changelog entries get sub-bullets:** past roughly three sentences, a bullet stops being scannable — the defect, its blast radius, the fix, the precedent and the caveat all run together, so a reader looking for any one of them has to parse all five. Lead with one sentence naming *what changed*, then one sub-bullet per distinct claim: impact, fix, behaviour-change warning, cost, migration note. A useful trigger is length — compare against the file's own median bullet and split anything several times longer, since that length almost always means several claims in one paragraph. Sub-bullets follow the same no-hard-wrap rule: one line each.

## What this project is

A private version of the [CMTAT](https://github.com/CMTA/CMTAT) security token, written in Noir/Aztec.nr for the [Aztec](https://aztec.network/) privacy L2. Balances and transfers are private (encrypted notes in each user's PXE) while `totalSupply`, pause state, roles and freeze/blacklist flags stay public; the issuer receives a duplicate of every note so it can audit activity for compliance. The repository is a prototype: it has **not** been audited, it is not upgradeable, and it has no gasless/meta-transaction support.

## Key concepts

- **Three deployment variants, one library.** `CMTATAztec` (base), `CMTATAztecDebt` (adds credit events and debt) and `CMTATAztecLight` (drops the validation module) are separate packages that compose modules from `cmtat_aztec_lib`. Since the token-module refactor (`doc/technical/token-module.md`) the value-moving chains are in the library too, so what a `main.nr` carries on those paths is the `#[external]` declarations, their attributes, the `enqueue_self` calls, the event emissions and one `#[contract_library_method] fn screening(storage)` returning `FreezeAndLists` (base, Debt) or `FreezeOnly` (Light) — the only variant-specific line. Do not add logic to those entry points; add it to `tokenModule.nr` so all three get it. Two more packages, `CMTATAztecAuth` and `CMTATAztecAuthMultiToken`, are **not tokens**: they are ARC-403 authorization contracts built from the same modules that apply pause, deactivation, freeze and a **sender-side** blacklist / whitelist to the `aztec-standards` AIP-20 `Token` / ARC-1155 `MultiToken` through the hook those tokens call before every transfer and burn (`doc/auth/README.md`). Two contracts because the hook signatures differ (`id` on the MultiToken) and Noir has no overloading; the rules live once in `lib/src/modules/authorizationHookModule.nr`, keyed on the burn selectors of the reference contracts, and the private hook checks the freeze and list flags in private and enqueues one public call carrying only `is_burn` for the pause/deactivation check (the H-3 decision applied). The hook never receives the recipient, so nothing screens `to` — a listed or frozen address can still receive; do not present the list as equivalent to the token contracts'. AIP-721 has no hook in the fork, so it is not covered. There is deliberately **no** CMTAT-flavoured copy of the AIP-20 token in this repository: Noir has no inheritance, so "extending" the standard would mean carrying its source verbatim, which was tried and rejected; CMTAT surface for a stock AIP-20 token goes into the authorization contract, or into the fork itself. Adding an entry point to a shared module means adding it to **every variant that should expose it** — there is no inheritance to do it for you. Keep the three `main.nr` files in step.
- **Single contract, module structs.** Noir has no Solidity-style inheritance, so "modules" are plain structs implementing `StateVariable<N, Context>` (which supplies both `new` and `get_storage_slot`) and held as fields of the contract's `#[storage] struct Storage<Context>`. Every user-callable entry point must be re-declared in `src/main.nr` — a module method alone is not callable. `ValidationModule<T, Context>` and `Freezable<T, Context>` are generic in their per-address flag type: `T` must implement the `pub` traits `UserFlagsTrait` / `FreezableFlagTrait` (plus `Eq + Packable`, and `ToField + FromField` for the list), which is how a downstream contract adds flags of its own; the module enforces only its own predicates, extra flags are the downstream contract's to check. Adding a method to either trait is a MAJOR change — every downstream implementor breaks.
- **Access control is public.** `AccessControlModule` maps `role: Field -> AztecAddress -> bool` in public state; roles are numeric globals (`DEFAULT_ADMIN_ROLE = 1`, `PAUSE_ROLE = 2`, `ENFORCEMENT_ROLE = 3`, `VALIDATION_ROLE = 4`, `ADDRESS_LIST_ADD_ROLE = 5`, `ADDRESS_LIST_REMOVE_ROLE = 6`, `MINTER_ROLE = 7`, `BURNER_ROLE = 8`, `DEBT_ROLE = 9`, `DEBT_CREDIT_EVENT_ROLE = 10`, `EXTRA_INFORMATION_ROLE = 11`). Because the check is public, private entry points enqueue a public `_mint`/`_transfer`/`_burn` that performs both the role check and the pause check. Public-context module methods take `PublicContext` by value, not `&mut PublicContext`.
- **Private/public split per operation.** `mint_to_private`, `transfer_private_to_private`, `burn` are `#[external("private")]`: they call the shared chain in `lib/src/modules/tokenModule.nr` (`mint_private` / `transfer_private` / `burn_private`: screening through the variant's `Screening` value, then the note movement with the issuer's copy), then `self.enqueue_self` a `#[external("public")] #[only_self]` counterpart whose body is also in the module (`mint_public` / `require_transfer` / `burn_public`) and that updates `total_supply` and performs the role check plus the lifecycle check — **not-paused for `_transfer`, not-deactivated for `_mint` and `_burn`**, matching CMTAT Solidity, where a pause stops transfers but not issuance or redemption. A revert in the public part reverts the whole tx.
- **Balances are note sets.** `private_balances` is an `Owned<BalanceSet<Context>>` using the `balance_set` aztec-nr library, reached as `.at(address)`; a balance is the sum of a user's `UintNote`s. `add`/`sub` return a `MaybeNoteMessage` that must be delivered: the owner's copy goes out with `.deliver(MessageDelivery::onchain_constrained())` and the issuer's audit copy with `.deliver_to(issuer, MessageDelivery::offchain())`. The `Transfer` **event** is different: it goes `onchain_constrained` to both the recipient and the issuer — an event has no owner and no nullifier, so the issuer's PXE can process it, which it cannot do with a note copy it does not own (by either delivery mode; 0.4.0 review, H-10). Since 0.4.0 mints (`from = 0`) and burns (`to = 0`) deliver the same event constrained to the issuer, so the `Transfer` stream is the issuer's complete, unforgeable ledger and the note copies are only corroboration. Do not downgrade any of them to `onchain_unconstrained` (the receipt becomes forgeable by the sender) and do not remove the mint / burn ones to save their ~24,000 gates each: they are what makes the audit story true.
- **`DelayedPublicMutable` delay.** `issuer_address`, freeze flags and validation flags are `DelayedPublicMutable` with an **initial** delay `CHANGE_ROLES_DELAY_SECONDS = 3600` (one hour; the library's constant, re-exported by each token), so they are readable from private functions without leaking the caller. The delay is a duration in seconds, not a block count, and nothing that reads one of these works until it has elapsed — including every mint, transfer and burn, which all read `issuer_address`. A private read sets the transaction's `expiration_timestamp`, so every value-moving transaction expires one delay after its anchor block, and that expiration is public (H-6 weighs 360 s, one hour and the 24 h the framework's own compliance token uses). The setting is **adjustable at runtime**: `set_roles_delay` (`DEFAULT_ADMIN_ROLE`, bounded by `MAX_ROLES_DELAY_SECONDS = 86400`) writes `roles_delay`, applies it to the single instances (`issuer_address`, `operationsFlag`), and the per-address setters (`freeze`, `unfreeze`, `add_to_list`, `remove_from_list`) take the setting as their `delay` argument and apply it to the entry they write through `schedule_with_delay`, returning the scheduled `effective_at` that the events carry — a `Map` entry carries its own delay and cannot be changed from outside. The library makes an increase immediate and a decrease effective after the difference; do not "simplify" by writing `now + constant` into an event again. Keep it one value for every delayed variable; a mix fingerprints operations. The **pause flag is deliberately not delayed**: `is_paused` stays a `PublicMutable<bool>` checked in the enqueued `_transfer`, because a delayed pause would take effect only after the delay (hours, by the library's guidance) and the pause is the emergency lever — decided under `H-3`; the cost is that a transfer enqueues one argument-less public call that reveals a transfer of this token occurred. Do not "fix" that by moving the flag to `DelayedPublicMutable`. The issuer is rotated with `set_issuer` (`DEFAULT_ADMIN_ROLE`, emits `IssuerChanged` with `effective_at`); a rotation redirects *future* audit copies only — delivered copies stay with the previous issuer.
- **Note budget.** A debit (`tokenModule::debit_private`) tries `DEBIT_INITIAL_MAX_NOTES = 2` notes, then the contract calls its own `#[only_self] _recurse_debit` at `DEBIT_RECURSIVE_MAX_NOTES = 8` per call until the amount is covered — AIP-20's scheme (credited in the code), applied under review finding A-5 for −42,000 gates on every debit. The recursion is a closure the four chains take, because a library cannot call the contract; every variant's `main.nr` declares `_recurse_debit` and passes `|a, r| self.call_self._recurse_debit(a, r)`. Do not replace `try_debit` with `BalanceSet::sub` to "simplify": that re-sizes every circuit for 16 notes. A fragmented balance costs one nested call per eight notes rather than failing.
- **Batching caps.** Two globals, both **measured, not derived**. `MAX_ADDR_PER_CALL = 4` for `mint_batch` and `burn_batch` (5 breaks them). `MAX_TRANSFER_ADDR_PER_CALL = 2` for `transfer_batch` (3 and above abort with `push out of bounds`), lower because each recipient costs four constrained deliveries once the `Transfer` event is delivered constrained to both the recipient and the issuer. The nested-private-call limit is irrelevant: the chains are library functions (formerly `#[internal]` helpers), inlined either way, so a batch makes no nested calls. Raising this global means re-running the suite at the new value and updating every batch test's array literals, not re-reading the protocol constants; see *Batching limits* in `doc/README.md`.
- **Authwits.** `transfer_private_to_private` and `transfer_batch` carry `#[authorize_once("from", "authwit_nonce")]`; `burn` and `burn_batch` carry `#[authorize_once("account", "authwit_nonce")]`, following the CMTAT Solidity naming. The macro takes the parameter **by name**, so renaming that parameter means editing the attribute too. It validates the authwit when `msg_sender()` differs from that account and nullifies the nonce to prevent replay; the account itself must pass `authwit_nonce = 0`. `cancel_authwit` pushes the authwit nullifier. `mint_to_private` deliberately has no authwit — only the minter role may mint.
- **Private/public bridges (hybrid).** The four AIP-20 bridges (`transfer_private_to_public`, `transfer_public_to_private`, `transfer_private_to_commitment` + `initialize_transfer_commitment`, `transfer_private_to_public_with_commitment`) and `balance_of_public` exist in all three variants behind the constructor's last argument `public_side_enabled: bool` (`PublicImmutable`, read in the private half, so a disabled bridge reverts before touching state and enqueues nothing). Their private halves run the same freeze/list screening as `transfer_private_to_private` and deliver the issuer's note copies; the public halves `_credit_public(to, amount)` / `_debit_public(from, amount)` assert not-paused and **publish their arguments by design** (the mover's own side). The recipient of a commitment is screened at `initialize_transfer_commitment`, and the issuer gets a constrained `CommitmentInitialized` event because the library delivers the partial note to `to` alone. A commitment can be **paid exactly once**: `pay_commitment` pushes `commitment_paid_nullifier(C)` next to the completion (K-6) — a deliberate difference from AIP-20, whose `complete` is not single-use and whose second payment is lost to the recipient; do not remove it to "match the standard", the framework itself leaves this guarantee to contract logic (aztec-packages #14364). Deliberately absent: commitment expiry, `transfer_public_to_public`, `mint_to_public`, `burn_public`. State and helpers are in `lib/src/modules/hybridModule.nr`, which is **MIT-only** (derived from aztec-standards, © Wonderland) — keep its header, and do not move code out of it into dual-licensed files without checking provenance.
- **AIP-20 private profile.** Since 0.4.0 the entry points `transfer_private_to_private`, `mint_to_private`, `name`, `symbol`, `decimals`, `balance_of_private` and `total_supply` carry the exact names and parameter types of the `aztec-standards` AIP-20 `Token`, so they answer its selectors (pinned in `tests/cmtat-aztec/src/test_aip20_profile.nr`). `burn` is deliberately **not** `burn_private`: AIP-20's is holder-authorised, ours needs `BURNER_ROLE`, and an identical selector with different authorisation would mislead wallets. This is a partial profile, not AIP-20 conformance — no public-balance or commitment paths — and the README says so; do not rename `burn` or the batch functions to "complete" it.
- **No force transfer.** Unlike Solidity CMTAT the issuer cannot move a user's notes; the compliance workaround is freezing the account (see "Limitations" in `doc/README.md`).
- **Issuer audit copies go offchain.** The issuer's copy of each note uses `MessageDelivery::offchain()`, not `onchain_constrained()`. PXE cannot process an onchain note message addressed to a non-owner — note discovery computes the note's nullifier, which needs the owner's key — so an onchain copy compiles but breaks discovery. The trade-off (no onchain data availability for the issuer's copy) is documented in `doc/README.md` and the CHANGELOG; do not "fix" this back to onchain without re-testing.

## Other important files

- `doc/README.md` — the specification: assumptions, per-operation privacy requirements, module design, known limitations. Read before changing behaviour. The root `README.md` is deliberately short (what, variants, quick start, where to read next); keep the detail in `doc/README.md` and link to it rather than growing the root file again.
- `doc/technical/cmtat-vs-aip20.md` — detailed comparison of CMTAT against Aztec's AIP-20 fungible-token standard, why this contract is deliberately **not** AIP-20 (public balances and partial notes both conflict with transfer restriction), and suggestions in both directions. Read it before proposing AIP-20 conformance.
- `doc/technical/building-on-aip20.md` — whether this project could be rebuilt on the `aztec-standards` library. Answer: no. Every crate there is `type = "contract"`, so there is nothing to depend on, and AIP-20's ARC-403 authorization hook is not passed the transfer recipient, so it cannot express CMTAT's screening. Forking the library and moving it to `v5.2.0` was tried and is trivial (eleven manifest edits, no source changes, 79/79 tests pass) — so "hard to port" is **not** the reason; the design conflicts are. Separately, *interface* alignment is cheap: selectors ignore parameter names, so renaming five entry points would match AIP-20's private-path selectors exactly, but `burn` must not be aliased to `burn_private` because the authorisation differs. Read it before proposing a rewrite on top of AIP-20.
- `doc/auth/README.md` — the two authorization contracts, user-facing: rules and their CMTAT Solidity counterparts, differences with the token contracts, deployment and operation, limitations, versioning, and the verification (unit tests plus an integration run against the real fork tokens, whose procedure and sources are in `doc/auth/integration-test.md` because the fork cannot be built in place).

Read it before touching the commitment paths.

## Common commands

- `yarn install` — install JS dependencies.
- `yarn compile` — `aztec compile --workspace` (override the binary with `AZTEC_COMPILE`); builds all three variants. It must be `aztec compile`, not `aztec-nargo compile`: at 5.2.0 `aztec-nargo` is a bare symlink to `nargo` and does not run the AVM transpiler, so `yarn codegen` then fails with `Contract's public bytecode has not been transpiled`.
- `yarn codegen` — generate TS artifacts from `target/` into `src/artifacts/` (required before any TS test or script).
- `yarn test` — `test:nr` (Noir `aztec test`) then `test:js` (Jest e2e); the e2e suite needs a running local network (`aztec start --local-network`; `--sandbox` was removed at Aztec 3.0) and a `.env` carrying `L1_MNEMONIC` (`cp .env.example .env`; the L1 credential is deliberately not a literal in the source, see `src/utils/l1_dev_account.ts`). Set `SKIP_SANDBOX=true` when a network is already up, so the suite does not spawn its own.
- `yarn test:nr` / `yarn test:js` — run one suite only. `test:nr` is `aztec test --workspace`; `aztec test --package cmtat_aztec_test` (or `cmtat_aztec_debt_test`, `…_light_test`, `…_auth_test`, `…_auth_multitoken_test`) runs one crate, and a trailing substring filters by test name (a plain substring, not a regex — `a|b` matches nothing). `aztec test` runs a bare `aztec compile` first, which rebuilds **every** member only because the workspace `Nargo.toml` has **no `default-member`** — do not add one back: with it, `aztec test` recompiled the base token alone and ran the other four contracts against stale `target/` artifacts (0.4.0 review, K-1).
- `yarn deploy`, `yarn deploy-account`, `yarn interaction`, `yarn multiple-pxe`, `yarn get-block`, `yarn fees`, `yarn profile` — testnet scripts (need `.env`).
- `yarn typecheck` — type-check the TypeScript with the compiler pinned in `package.json`. Do not run `npx tsc`: the Aztec toolchain ships its own `tsc` at `~/.aztec/current/node_modules/.bin/`, which lands on `PATH` ahead of `./node_modules/.bin` and type-checks the project with the wrong compiler version.
- `yarn clean` / `yarn clear-store` — drop `src/artifacts`, `target`, `codegenCache.json` / drop the local PXE `store`.

## Conventions

- Noir sources use `camelCase` file names for modules (`access_controlModule.nr`, `validationModule.nr`) and snake_case for functions; keep the existing style rather than renaming.
- Every new public/private entry point goes in `src/main.nr` under the matching banner comment block (`AUTHORIZATION MODULE`, `VALIDATION MODULE`, `MINT`, `TRANSFER`, `BURN`, `INTERNAL`, `UNCONSTRAINED`), with a NatSpec-style `@dev` / `Requirements:` comment.
- Any state-mutating operation must keep the invariant chain, which now lives in `tokenModule.nr`: freeze check + validation check in the private chain (the `Screening` trait) (the validation check screens **both parties** of a transfer, the **recipient** of a mint and the **account** of a burn, as CMTAT Solidity's `_canMintBurnByModule` does), role check + lifecycle check in the enqueued public internal function. The lifecycle check differs by operation and this is deliberate: `_transfer` asserts not-paused, `_mint` and `_burn` assert not-deactivated. A pause therefore stops transfers only, as in CMTAT Solidity; `deactivate_contract` requires an existing pause and blocks `unpause_contract` forever, which stops transfers, and the explicit not-deactivated check is what stops mint and burn.
- Any note written for a user must also be delivered to the current `issuer_address` — auditability is a hard requirement of the design. The issuer's copy uses `MessageDelivery::offchain()`; see the key concept above before changing that.
- Every behaviour change needs a Noir test in the contract's test crate under `tests/<contract>/src/` (and an e2e test when it crosses the TS boundary) — **never** in the contract crate: `aztec compile` warns `Found tests in contract crate(s)`, and a test edit would invalidate the contract artifact (J-2, fixed in 0.4.0 following the layout the Aztec docs scaffold). A test crate imports its contract by package name (`use cmtat_aztec::CMTATAztec as Token`) and deploys it with `env.deploy("@cmtat_aztec/CMTATAztec")`; tests build their world through that crate's `utils.nr` `setup*` helpers. A negative test must name the assert it reaches (`should_fail_with`) with the setup granting every role the path needs first; a test of a delayed value needs its before-delay twin; the issuer-copy invariant is asserted through `env.offchain_messages()` (`test_issuer_copies.nr`); measured facts (the two-note initial budget and the recursion past it, the private-balance slot `22`, the refused second payment into a reused commitment) are pinned in `test_edge_cases.nr` — a change that moves one of them must update the test *and* the README sentence that quotes the number; the Debt and Light variants pin their shared selectors in `test_selectors.nr` because their declarations are the one thing the token module does not share. Before trusting a green suite after a change to a chain, break the chain on purpose and watch the test fail — two invariants survived that check in the 0.4.0 review. Those `setup*` helpers and `check_private_balance` are **deliberately triplicated** across the variants: they name the variant's contract type and deploy string, which a shared crate cannot. Helpers that do not name a contract (`advance_past_delay`, `call_private_on_behalf_of`) live once in `test-helpers/` and are re-exported by each `utils.nr`; add new contract-agnostic helpers there, not in a variant.
- Bumping the Aztec version means updating `Nargo.toml`, `package.json` and the `aztec-up` version together — they must match. `aztec compile` warns when the dependency tag and the CLI disagree.
- The e2e suite and any operator runbook must account for the delay setting (`CHANGE_ROLES_DELAY_SECONDS` initially, `roles_delay()` afterwards): a scheduled value change is not readable until the delay has elapsed. The e2e suite does **not** wait it out: `src/utils/time_travel.ts` warps the chain with `RollupCheatCodes.advanceToSlot` and syncs the client's clock, which works because a local network's L1 is anvil. It falls back to sleeping when there are no cheat codes (a real network, or `E2E_REAL_CLOCK=true`), which is why the Jest timeout is derived from the delay rather than hard-coded.
